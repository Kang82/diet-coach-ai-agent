# B14 gpt-oss-120b(추론 low) 식단 생성 1회 (2026-11-08)

B14(T8-7) 중 한도가 모자라(남은 약 1,540 Neuron, 사용자 확인) gpt-oss-120b만 추론 low로 1회 돌려 시간과 품질을 보려 했다. 조건은 사용자가 정한 대로 외식 메뉴가 많은 프로필(새 픽스처 페르소나 E). **식단표까지 가지 못했다.** Flue와 Workers AI gpt-oss의 메시지 형식이 맞지 않아 두 번째 요청부터 400으로 거절됐다.

## 질문

- gpt-oss-120b(추론 low)는 메뉴 많은 프로필에서 시간 안에, 규칙을 지키는 식단표를 내나. 생성 시간·출력 토큰·Neuron·문장 품질은 gemma(사용자 기록 출력 약 15,000토큰, 275~347초)와 어떻게 다른가

## 방법

- 준비(코드, 단위 테스트): 
  - gpt-oss-120b는 Workers AI 스키마상 기본 출력 상한이 256토큰이라 Flue가 상한을 보내지 않으면 잘린다. `src/agents/output-caps.ts`로 공급자의 `stream`을 감싸 이 모델에만 `maxTokens` 16,384를 넣고, `src/agents/provider.ts`에서 `setProvider`로 등록했다(빌드에서 생성된 기본 등록은 `!hasProvider("cloudflare")`로 건너뜀)
  - 식단 생성 모델을 `.dev.vars`의 `PLAN_MODEL`로 바꿀 수 있게 했다(`models.ts` `planModel`, 후보 `gptOss120b`, 단가 31,818 / 68,182)
  - 페르소나 E(`core/__fixtures__/personas.ts`): 감량 + 혈당, 피할 음식 유제품·견과, 평일 점심 외식 20개·저녁 15개(겹침 5, 분류 30개), 주말 집밥
- 로컬 개발 서버, `.dev.vars`에 `PLAN_MODEL=gptOss120b`, `PLAN_THINKING=low`, `MENU_CLASSIFIER=demo`(분류는 가짜, 평가가 픽스처 분류로 덮어씀). 로컬 카운터를 비우고 `EVAL_RUNS=1 npm run evals -- -t 페르소나E` 1회
- AI Gateway `default` 로그(요청·응답 본문)로 호출을 봤다. Cloudflare GraphQL은 호출 한도(rate limit)에 걸려 시작 전 사용량을 확인하지 못했다. 사용자가 알려 준 남은 양(1,540)을 기준으로 진행했다

## 비용

gpt-oss 1회(입력 1,907, 출력 110토큰) ≈ 68 Neuron, 400 4회는 0토큰. 바깥 턴 gemma 3회(입력 862~3,075, 출력 87~150) ≈ 약 50 Neuron. 합계 약 120 Neuron

## 결과

- 평가 결과: 도구 `error`, 약 33초(평가 1회차 32.6초)
- 출력 상한 감싸기는 동작했다. 요청 본문에 `max_completion_tokens: 16384`, `reasoning_effort: "low"`가 들어갔다
- 첫 요청(17:08:43, 200): gpt-oss가 추론("We need to produce 14 cells … Need call create_week_plan tool first? System says …") 뒤 `finish`가 아니라 **`create_week_plan`을 불렀다**. 도구 안 `harness.prompt`가 에이전트의 시스템 지시문("create_week_plan 도구를 한 번 부르세요")과 도구 목록(`task`, `create_week_plan`, `finish`, `give_up`)을 그대로 물려받기 때문이다. gemma는 지금까지 이 지시를 따르지 않고 `finish`를 불러 드러나지 않았다
- Flue가 재귀 호출을 막았다(도구 결과 "[flue] Harness tool "create_week_plan" cannot be invoked recursively while it is already active.")
- 두 번째 요청부터(4회) **400 `AiError 5006 Bad input`**: Workers AI gpt-oss의 입력 스키마가 Flue의 여러 턴 메시지 형식을 받지 않는다. 사용자 메시지 `content`가 배열, 도구를 부른 assistant 메시지 `content`가 `null`인 것이 스키마(`content`는 문자열)와 맞지 않는다는 오류였다. 첫 요청(system 문자열 + user 배열)은 통과했으므로 문제는 assistant `null`·tool 메시지가 붙는 두 번째 턴부터다
- 그래서 시간·품질은 재지 못했다. 400은 재요청 대상이 아니라 Flue가 곧바로 실패로 끝내 Neuron을 거의 쓰지 않았다

## 결론과 다음

- 지금 Flue 2.3.0 + Workers AI 바인딩으로는 gpt-oss-120b를 식단 생성에 그대로 쓸 수 없다. 구조화 출력이 첫 턴에 `finish`로 끝나지 않으면(재요청, 다른 도구 호출) 두 번째 턴이 400이 된다
- 쓰려면 둘 다 필요하다(코드 변경, 새 계획)
  1. 메시지 형식 맞추기: `output-caps.ts`처럼 공급자를 감싸 gpt-oss 요청의 `onPayload`에서 배열 `content`를 문자열로 합치고 `null`을 `""`로 바꾼다
  2. 도구 안 프롬프트가 에이전트 지시문·도구를 물려받는 문제: 식단 생성 프롬프트에 "finish만 부르라"를 분명히 하거나, 물려받지 않는 방법을 Flue 문서에서 찾는다. gemma에도 잠재 위험이다(지시문이 "create_week_plan을 부르라"고 말하는 상태)
- 다른 후보(mistral-small)도 같은 형식 문제가 있을 수 있다. 다음 비교 전에 짧은 2턴 호출로 형식부터 확인한다
- 새 코드(출력 상한 감싸기, `PLAN_MODEL`, 페르소나 E)는 남긴다. 기본 동작(gemma, 상한 없음)은 바뀌지 않는다
