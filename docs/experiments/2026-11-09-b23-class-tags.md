# 메뉴 분류에서 태그 정하기 실제 확인 (2026-11-09, B23 T13-4, 로컬)

## 목적
- T13-4: 외식 메뉴 태그를 분류가 메뉴마다 한 번 정하고, 외식 칸 태그를 코드가 채우는 변경(B23)이 실제 모델에서 되는지
- 분류 출력이 늘어 시간·Neuron이 얼마나 느는지(태그 전 페르소나 E 분류는 약 180 Neuron으로 어림)

## 방법
- 로컬 개발 서버(5173), 실제 모델. 페르소나 E: 감량 + 혈당, 피할 음식 유제품·견과, 외식 메뉴 30개
- (1) 평가 세트 `EVAL_RUNS=2 -t 페르소나E`, 분류 gemma
- (2) 분류 스키마가 쉼표 문자열을 받게 고친 뒤 분류만 2회(스크래치 스크립트, 인터뷰 제출 + 분류 요청), gemma
- (3) 분류 모델을 gpt-oss-120b(low)로 바꾼 뒤 분류만 2회 + 평가 세트 1회
- 대화 기록은 로컬 Durable Object 저장소(`flue_conversation_stream_batches`)에서 읽었다

## 비용
- 로컬 카운터(`usage_hourly` 13시 UTC 칸) 5,689 Neuron(시간 초과는 걸린 시간 × 2로 셈). 시작 전 계정 최근 24시간 3,641(GraphQL, 13:03 UTC)이라 끝난 뒤 약 9,300으로 어림. 계획(1,000~1,500)을 크게 넘어 멈췄다

- 만들기(gpt-oss)는 두 번 모두 첫 생성 통과, 다시 추천 0회(70초 421 Neuron, 40초 388 Neuron). 외식 칸 태그가 분류 태그와 모두 같았다(어긋난 칸 0)
- 태그 일관성: 같은 회차 안에서는 메뉴마다 하나로 정해진다. 모델·회차 사이에는 다르다(예: 된장찌개 gemma `soy` / gpt-oss `soy, meat, pork`, 쌀국수 gemma `meat, beef, refined_carb_main` / gpt-oss `refined_carb_main`). 샌드위치는 세 번 모두 `dairy`가 붙어 피하기(유제품)
- 메뉴 11개(배포본 사용자 실행, 태그 전)는 gemma 70초 104 Neuron이었다. 메뉴 수가 많을수록 출력이 길어지고, 긴 JSON 한 번에서 깨지거나 빠지는 일이 잦다

## 결론과 영향
- 코드 보정(외식 칸 태그 = 분류 태그, 사전 점검 태그 한도, 프롬프트 태그 표시)은 의도대로 동작한다
- 하지만 메뉴 30개를 한 번에 분류하면 gemma는 시간 제한을 넘기고(3회 중 2회+2회), gpt-oss는 통과해도 다시 묻기로 400~1,800 Neuron이 든다. 태그를 더하기 전(약 180)보다 크게 비싸다
- 분류 스키마: 쉼표로 이은 criterionIds·tags를 나눠 받게 했다(gemma 실패 원인 하나). gpt-oss의 "모르는 criterionId"도 코드가 지우면 되므로 스키마에서 받는 쪽을 후보로 둔다
- **사용자 결정(2026-11-09): 되돌린다.** 분류 프롬프트에서 tags를 빼고 분류 모델은 gemma로 돌린다. 쉼표 문자열 받기는 남긴다. 태그가 있는 분류를 쓰는 코드(외식 칸 채우기, 사전 점검 한도, 생성 프롬프트 표시, 피할 음식 → 피하기, 화면 한 줄)는 남겨 두되 tags가 없으면 동작하지 않는다. T13-4·열린 질문 3은 열어 둔다

## 남은 의문
- 메뉴를 나눠 부르면 호출당 출력이 짧아져 깨짐·빠짐이 줄어드는지
- 분류 시간 제한 3분이 메뉴 30개에 맞는지
