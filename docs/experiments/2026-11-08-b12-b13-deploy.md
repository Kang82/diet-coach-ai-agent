# B12 + B13 세 번째 배포와 배포본 실제 1회 (2026-11-08)

B12(식단 도구 durable)와 B13(한도 보호 보강)을 함께 배포하고, 배포본에서 식단표를 한 번 만들어 두 묶음의 확인 항목을 함께 봤다(사용자 결정 11-08: 실제 확인을 한 번으로).

## 질문

- 배포본에서 만들기가 정상 경로로 끝나나(durable step, 게이트, 예약 정산이 붙은 상태)
- B12 쪽: Workers Traces span에 대화 내용이 없나, 도구 안 Flue `log.info`가 Workers Logs에 나오나, 원격 `usage_hourly`에 새 시간 칸이 생기나, Durable Object 알람 하나가 응답 전체를 붙잡나(15분 가설)
- B13 쪽: 도구가 끝나면 원격 `usage_reservations`가 비나, `usage_daily`에 종류별 횟수가 남나

## 방법

- 시작 전 Cloudflare GraphQL `aiInferenceAdaptiveGroups` 최근 24시간 합계 **7,472 Neuron**(16:17 UTC). 분류 + 만들기 어림 600을 더해도 10,000 아래
- 원격 D1에 0004 적용 → 바로 `npm run deploy`(버전 `f802d3d7`, 커밋 `0be4b45`까지). ping 200, 토큰 없는 `/api/me`·메시지 POST 401
- 원격 사용자 토큰을 새로 발급(사용자 ID `efab2710a0cdc7a0`, 확인용). 기존 사용자 링크는 그대로
- 페르소나 A로 인터뷰 제출(LLM 없음) → 메뉴 분류(실제 gemma) → 식단표 만들기(실제 gemma). `src/evals/support/prepare.ts`와 같은 순서, `DIET_COACH_URL`을 배포본으로
- Workers Observability telemetry query API(Cloudflare MCP)로 이벤트 종류, 알람 호출 시간, gemma `chat` span 속성을 봄. 원격 D1은 `wrangler d1 execute --remote`

원격 `usage_hourly` 16시(UTC) 칸이 실행 뒤 633(분류 + 만들기 310 + 바깥 턴). 같은 시각 다른 사용자의 분류도 이 칸에 들어갔을 수 있다(아래).

## 결과

| 단계 | 시간 | 결과 |
| --- | --- | --- |
| 인터뷰 + 분류 | 92초 | 통과 |
| 만들기 | 252초(도구 245초) | `ok`, 다시 추천 0, 출력 8,641토큰, 310 Neuron, 도구 호출 1번 |

- 요약: "유제품 0회 / 주 1회 이하 메뉴: 돈가스 1회 / 같은 메뉴 연속 없음". 주가 밀리지 않아 T10-5 안내는 없음(의료 안내 1줄)
- **예약(B13)**: 분류 중에는 이 대화 키로 360이 걸려 있었고, 만들기가 끝난 뒤 이 대화 예약은 없었다. `usage_daily`: `user:` 3, `classify:` 1, `plan:` 1
- **`usage_hourly`(B12 확인 1)**: `2026-11-07T16` 칸이 새로 생겼다(실행 직후 633)
- **Traces 내용(B12 확인 2)**: gemma `chat` span의 속성은 모델, 추론 수준, 토큰 수, finish_reason, 대화·제출 ID뿐이었다. 한글이나 프롬프트·메시지 필드는 없었다(`content: false` 동작)
- **도구 `log.info`(B12 확인 3)**: Workers Logs 이벤트 종류는 `span`, `request-logs`, `cf-worker-event`뿐이었고 console 로그 종류가 없었다. Flue 도구 `log`는 대화 스트림(로그 이벤트)으로만 가고 Workers Logs에는 나오지 않는다. 도구 단위 정보는 span(`chat`, `ai_run`)과 AI Gateway 로그로 본다
- **알람 15분 가설(B12 확인 4)**: 실행 동안 `FlueDietCoachAgent` 알람 호출은 30번, 가장 긴 것이 19초였다. 4분짜리 만들기 동안 알람은 약 10~20초 간격으로 짧게 깨어날 뿐 응답 전체를 붙잡지 않았다. 그래서 "알람 하나가 두 제출을 15분 넘게 이어 처리해 잘렸다"는 가설은 맞지 않는 것으로 본다. 11-06 재시작 원인은 여전히 모른다(배포·런타임 업데이트 등). B12로 재시작돼도 결과가 남으니 더 쫓지 않는다

## 결론

- B12·B13이 들어간 배포본에서 만들기가 정상으로 끝나고, 예약이 걸렸다가 정산되며, 종류별 횟수가 쌓인다
- Traces에는 대화 내용이 없다. 도구 `log.info`는 Workers Logs에 나오지 않는다(문서 갱신)
- 알람 15분 가설은 맞지 않는 것으로 정리한다

## 추가 확인 (16:28~16:39 UTC)

- 기존 사용자의 만들기는 **`timeout`으로 끝났다**(사용자 화면 "식단표를 만들지 못했어요 / 응답이 너무 오래 걸려 멈췄어요"로 확인). 처음 이 절에 "생성 5분 + 다시 추천 3분, 예산 안에 끝남"이라고 적었던 것은 잘못 읽은 것이다
- AI Gateway 로그(시각은 호출이 끝난 때): 생성 호출이 16:28:17에 시작해 300.3초 뒤 16:33:17에 끝났지만 출력 토큰 1(응답이 오지 않음). Flue `streamIdleTimeoutMs`(기본 5분)가 끊고 같은 요청을 16:33:18에 다시 보냈고, 우리 생성 호출 상한 8분(첫 시작 기준, 16:36:17)에 걸려 177.6초 만에 우리가 끊었다(499). 다시 추천은 없었다
- 원인은 Workers AI 쪽 일시 멈춤으로 보인다. 후속은 tasks.md T8-6(후순위)
- 끝난 뒤(16:39) 원격 `usage_reservations`는 비었다. 분류 → 만들기 → 끝까지 예약이 걸렸다가 정산됐다
- 원격 `usage_hourly` 16시 칸은 1,932가 됐다(그 만들기 약 991, 대부분 끊긴 호출을 걸린 시간 × 2로 센 것). 같은 시각 Cloudflare GraphQL 16시 칸은 1,320이라 우리 카운터가 더 크게 센다(더 막는 쪽)
- Cloudflare GraphQL 최근 24시간 합계 **8,457**(16:39 UTC). `2026-11-07T00` 칸(1,099)은 11-08 00:00 UTC(한국 9시)에, 14·15시 칸(약 6,040)은 11-08 14·15시 UTC(한국 23시·24시)에 창에서 빠진다
- 원격 안전선 카운터(배포본 사용량만 셈)는 약 4,200이라 실제 한도(로컬 개발 사용량 포함)보다 먼저 막지 못한다. 로컬 개발과 배포본이 같은 계정 한도를 쓰는 한계는 그대로다(plan-upgrade.md)
