# B6 실제 끝까지 확인과 메뉴 분류 멈춤 (2026-11-06)

## 질문

- 첫 화면 분기 → 프로필 확인(고치기, 동의) → 기간 선택(일정) → 메뉴 분류 → 식단표가 실제 모델로 끝까지 되나 (T5 전체 완료 기준)
- 진행 중 생긴 질문: 메뉴 분류(`classify_menus`)가 왜 끝나지 않나

## 방법

- 개발 서버, 가짜 모드 끔. Chrome에서 진행
- 인터뷰 단계는 B4에서 확인해서 생략했다. 페르소나 A의 끝난 답(목표 메모 "체중 5kg 감량, 콜레스테롤 관리")을 화면 진행 상태로 넣고 프로필 확인 화면부터 진행
- 멈춘 이유는 로컬 Durable Object 저장소의 harness 기록(`flue_conversation_stream_batches`)에서 찾았다. 로컬 탐색 API: `POST /cdn-cgi/local/explorer/api/workers/durable_objects/namespaces/diet-coach-FlueDietCoachAgent/query`
- 원본: [data/2026-11-06-b6-end-to-end.json](data/2026-11-06-b6-end-to-end.json)

## 비용

멈춘 실행 3번이 약 3,140 Neuron이다(harness 기록의 토큰 × llama-4-scout 단가). 마지막 성공 실행은 약 530 Neuron에, 60초에 끊긴 gemma 분류 1회(기록 없음)가 더해진다. 합쳐서 약 3,700~3,800 Neuron.

## 결과

### 메뉴 분류가 끝나지 않은 이유: llama-4-scout 출력 256토큰

| 실행 | 분류 모델 | 시간 제한 | harness 턴 | 멈춘 이유 | 어림 Neuron |
| --- | --- | --- | --- | --- | --- |
| 1 | llama-4-scout | 없음, 약 3분 뒤 `/abort` | 25 | `length` 24회 | 약 1,990 |
| 2 | llama-4-scout | 60초 | 9 | `length` 8회 | 약 550 |
| 3 (메모 없는 대화) | llama-4-scout | 60초 | 9 | `length` 8회 | 약 600 |

- 매 턴 `stopReason: "length"`, 출력 **256토큰**에서 잘렸다. Flue의 Workers AI 공급자는 `options.maxTokens`가 있을 때만 `max_completion_tokens`를 보낸다. 그런데 에이전트 루프가 이 값을 넘기지 않아 모델 기본값이 쓰였다. llama-4-scout의 기본값은 256으로 보인다(Pi 카탈로그에는 16,384로 적혀 있지만 요청에 실리지 않는다).
- 잘린 출력에는 `finish` 호출이 없어 Flue가 다시 요청을 보낸다. 최대 33턴까지 간다(`runWithResultTools`의 `MAX_FOLLOWUPS = 32`). 한 턴이 입력 약 2,000토큰이라 약 65~75 Neuron씩 쌓였다.
- B5에서 같은 분류가 7초에 통과한 것도 출력이 정확히 256토큰이었다. 우연히 상한 안에 들어온 것이다.
- 목표 메모 확인은 출력이 27토큰이라 llama-4-scout로도 문제없다.

### gemma로 바꾼 뒤

- 시간 제한 60초에서는 첫 턴 추론 중에 끊겼다.
- 3분으로 늘리자 첫 `finish`가 검증에서 거절됐다. `criterionIds`, `orderTips`를 배열 대신 문자열 하나로 냈기 때문이다(`"criterionIds": "reduce_saturated_fat"`). 두 번째 턴에서 통과했다. 95초, 입력 5,880 / 출력 4,675, 약 181 Neuron
- 분류: 국밥·돈가스·쌀국수 주 1회, 백반·회덮밥 often. 이유와 주문 팁이 모든 메뉴에 들어갔다(B5의 llama 결과보다 낫다).

### 끝까지 (b6-real3)

| 단계 | 시간 | Neuron |
| --- | --- | --- |
| 첫 화면 분기 "바뀐 항목 고치기" → 조리 시간 고치기 → 제출(목표 메모 확인, llama) | 약 10초 (도구 1초) | 39 + 바깥 턴 12 |
| 메뉴 분류 (gemma, 2턴) | 95초 | 181 + 바깥 턴 20 |
| 식단표 (gemma) | 168초 | 236 + 바깥 턴 19 |

- 식단표는 처음에 통과했다(다시 추천 0회). 수요일 저녁 "팀 회식" 칸은 비우고 13칸. 점검 요약은 "유제품 0회 / 주 1회 이하 메뉴: 쌀국수 1회, 돈가스 1회 / 같은 메뉴 연속 없음"
- 저장 동의는 저장한 프로필이 있어 처음부터 체크돼 있었다. 제출 결과에 `consentedAt`이 들어갔다.

## 결론과 영향

- 메뉴 분류 모델을 gemma로 바꿨다(`models.ts`의 `menuClassModel`). 분류 1회 예산은 약 180~200 Neuron, 1.5분이다.
- 짧은 LLM 호출에 시간 제한을 걸었다(`core/llm-timeout.ts`, `agents/prompt-call.ts`): 목표 메모 60초, 메뉴 분류 3분, 식단 생성 8분, 칸 다시 추천 4분. 넘으면 `timeout`으로 답하고 화면은 "다시 시도" 안내를 보여 준다.
- 메뉴 분류 스키마는 문자열 하나도 배열로 받는다(`agents/menu-schema.ts`).
- Flue의 구조화 출력 재요청은 최대 33턴이다. 출력이 잘리는 모델은 한도를 크게 쓸 수 있다. 새 모델을 쓰기 전에 출력 상한을 먼저 확인한다.

## 남은 의문

- Flue에서 `maxTokens`를 넘기는 공식 방법. 공급자를 감싸 `max_completion_tokens`를 넣으면 llama-4-scout(7초)로 돌아갈 수 있다
- 식단 생성 스키마(`plan-schema.ts`)도 gemma가 배열 대신 문자열을 낼 수 있다. 지금까지는 실패한 적이 없다
