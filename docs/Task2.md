# MVP 이후 고도화 후보 (초안)

`docs/tasks.md`의 B1~B14와 T1-7까지를 MVP(기획서 "첫 시연" 범위)로 보고, 그 뒤에 붙일 만한 일을 모은다. 2026-11-07에 기획서, 스펙(0·2·3·10·11장), `plan-upgrade.md`, `tasks.md` "나중에" 절을 보고 정리했고, 2026-11-08에 B11 결과와 B14(실제 사용자 생성 실패)를 반영했다.

> ID 기호는 `tasks.md`(B 묶음, T task)와 저장소 이름 D1과 겹치지 않게 R(계속 쓰기)·Q(품질)·S(속도·비용)·F(기능)·O(운영)를 쓴다.

> 초안이다. 범위, 순서, Neuron 어림은 나중에 다시 정리한다. 진행하기로 한 항목은 `tasks.md`의 task와 묶음으로 옮기고, 묶음을 시작할 때 CLAUDE.md 방식대로 계획을 먼저 써서 승인받는다.

## 지금 상태와 빈 곳

- MVP는 **한 번 쓰고 끝나는 흐름**이다. 인터뷰 → 분류 → 1주일 식단표 → 칸 수정까지 된다.
- **단, 메뉴가 많은 실제 사용자에게서는 식단표 만들기가 아직 실패한다** (B14, T8-6). 배포본에서 사용자가 직접 만든 3번이 모두 시간 상한에 걸려 결과가 없었다(생성 출력 약 15,000토큰·5~6분, 마지막 1회는 약 960 Neuron을 쓰고 실패). 페르소나 픽스처(출력 5,700~10,700토큰)로만 확인해서 놓쳤다. 이 문서의 항목은 모두 식단표가 만들어진다는 전제 위에 있으므로 B14가 먼저다.
- 기획서 6장의 "계속 쓸 이유"(지난주를 이어서 짜기, 쓸수록 고칠 칸이 줄어듦)와 정식 운영 성공 기준(체크율 70%, 고친 칸 3개 이하인 주 비율)은 기능도 없고 잴 방법도 없다. 가장 큰 빈틈이다.
- 제약: 생성 1회 페르소나 기준 2~6분·약 250~400 Neuron, 메뉴 많은 프로필은 5~6분·약 430 Neuron 이상(gemma). 하루 무료 한도 10,000 (`plan-upgrade.md`). gpt-oss-120b(low)는 페르소나 E에서 72초·306 Neuron으로 1회 통과했다(B14 3차, 1회라 흔들림은 모름).

## 추천 순서

0. **B14 긴 생성과 모델 비교** (`tasks.md`, 이 문서의 항목이 아니라 선행 조건). S1은 B14의 해결 후보와 겹치므로 B14 결과를 보고 함께 정한다
1. **O2 로그인**
2. Neuron이 거의 들지 않고 가치가 큰 것: R1 지난 식단표 목록 → R2 체크 → R4 측정 기록, Q1 태그 사전, O1 대화 기록 지우기
3. 실측이 필요하지만 효과가 큰 것: S1 외식 칸 코드 배치(B14 결과를 보고), S2 바깥 턴 조사, R3 체크 반영 생성
4. 기획서의 다음 기능: F1 하루 재조정 → F2 레시피 → F3 근육 증가 → F4 도시락
5. 사용자를 늘릴 때: S3 미리 만들기, O3 기관 통계, O4 요금제

로그인을 맨 앞에 둔 이유 (사용자 결정, 2026-11-07):

- R1·R2·R4는 여러 주에 걸친 사용자 데이터다. 로그인 수단은 지금 `user_id`에 연결되므로(O2 비교 절) 먼저 쌓아도 데이터를 옮길 일은 없다. 문제는 지금 방식에서는 링크를 잃으면 그동안 쌓은 기록에 다시 들어올 수 없다는 점이고, 기록이 쌓일수록 잃는 것이 커진다. 그래서 기록이 쌓이기 시작하기 전에 로그인을 둔다
- O1(대화 기록 지우기)은 사용자별 대화 목록이 필요하다. 로그인과 같은 자리(사용자 식별, 가드, D1 `users`)를 고친다
- Neuron을 쓰지 않는다

## Q. 결과 품질 ("코드가 보장한다" 원칙을 넓히기)

- **Q1. 재료 → 태그 사전 (스펙 열린 질문 3).** 실측에서 태그가 여러 번 틀렸다(현미밥에 `refined_carb_main`, 백반·들깨에 `soy`, 소고기 볶음에 `fatty_meat` 빠짐). 칸의 `ingredients`로 코드 사전이 태그를 더하고 LLM 태그와 합친다. Neuron 0. 태그를 더하기만 하면 다시 추천이 늘 수 있으니, 지울 태그(오탐)를 따로 둘지 함께 정한다
- **Q2. 주재료 반복 제한 ("나중에").** Q1의 재료 정규화로 "닭가슴살 샐러드 / 닭가슴살 볶음" 같은 반복을 규칙으로 잡는다. `RULE_IDS`, 스펙 3.2·8.2 표를 함께 고친다
- **Q3. 분류 이유 품질.** 기준 ID를 반드시 고르게 하고, 이유 문장은 코드 템플릿으로 바꾸는 방안("일반적인 식사라 부합함" 문제)

## S. 속도와 비용

- **S1. 외식 칸 배치를 코드로.** 외식 칸 메뉴는 목록, 분류, 주 1회 규칙, 연속 금지라는 정해진 제약 안에서 고르는 조합 문제라 코드가 보장할 수 있다. 코드가 `menuId`를 배치하고 LLM은 태그·주문 팁·이유만 채우거나 집밥 칸만 만든다. 출력 토큰과 다시 추천이 함께 줄어든다. B11에서 추론 수준을 low로 낮춰도 출력 -7%, 시간은 같았으므로(효과 없음) 출력을 줄이는 쪽은 이 방법이 남는다. B14(T8-6) 할 일 2의 후보 "프롬프트에 넣는 메뉴 수 줄이기"와 같은 방향이라, 메뉴 많은 프로필의 시간 문제에도 직접 효과가 있을 수 있다. 모델을 바꾸면(T8-7) 필요성이 줄 수 있으니 B14 결과를 보고 정한다. 태그 제한(튀김 횟수 등)은 LLM 태그에 달려 있어 점검은 그대로 둔다. 실측 1회 약 300 Neuron
- **S2. 바깥 턴 줄이기.** 화면이 정해진 접두어 메시지를 보내므로 바깥 모델은 사실상 도구 하나를 부를 뿐이다. 이 턴은 시간과 Neuron(2~21)을 쓰고, 도구 결과의 식단표 JSON이 다음 턴 입력에 다시 들어가 대화가 길어질수록 입력이 커진다(칸 수정 턴 입력 2,234토큰, `tasks.md` "나중에"). 병렬 호출 위험(T10-2)은 B13에서 접두어에 맞는 도구 하나만 마운트해 막았다. Flue에서 도구를 직접 실행하거나 모델에게 결과를 짧은 요약만 보여 줄 수 있는지 `node_modules/@flue/runtime/docs/`부터 확인한다
- **S3. 미리 만들기.** 일요일 오후에 Cron Trigger로 다음 주 식단표를 만들어 두면 기다리지 않는다. 사용자가 늘면 Neuron 계획과 충돌하므로 안전선보다 낮은 별도 상한이 필요하다
- **S4. 진행 안내.** "몇 칸을 다시 고르는 중"(`useDataWriter`, "나중에"). 시간은 그대로지만 덜 답답하다

## O. 운영과 개인정보

- **O1. 대화 기록 지우기.** 건강 정보는 민감정보이고 기획서는 "언제든 지울 수 있게"를 약속했다. 지금은 프로필만 지워지고 Durable Object 대화는 남는다. 사용자를 늘리기 전에 한다
  - **AI Gateway 로그도 지울 대상이다** (2026-11-08 확인). Flue는 `cloudflare/…` 모델을 기본으로 `default` 게이트웨이를 거쳐 부르고(`provider.ts`도 기본값 그대로), 이 게이트웨이는 `collect_logs: true`, 최대 100,000건 보관(`DELETE_OLDEST`)이다. Gateway API에 로그별 요청·응답 본문 조회(`…/logs/{id}/request`, `…/response`)가 있어 프롬프트(목표, 피할 음식, 혈당 등)와 식단표가 남는다. 앱 트레이싱의 `content: false`와는 별개다. 본문은 열어 보지 않았다
  - 정할 것: (가) `cloudflareBindingProvider`의 `gateway` 옵션에 `collectLog: false`를 줘 로그를 끈다(토큰 수·시간도 함께 사라져 B10 이후 생성 지연을 찾던 근거가 없어진다), (나) 로그는 두되 `metadata`에 `userId`를 붙이고 지울 때 Gateway 로그 삭제 API(`DELETE …/logs`)로 그 사용자 것을 지운다, (다) 보관 건수를 줄인다. 어느 쪽이든 저장 동의 설명 문구를 함께 고친다
- **O2. 로그인 (스펙 열린 질문 2).** 지금은 고유 링크 토큰뿐이라 링크를 잃으면 데이터에 다시 들어올 수 없다
- **O3. 기관용 통계 (기획서 6장).** 개인 데이터 없이 이용 인원, 체크율 같은 집계만. R4가 먼저 있어야 한다
- **O4. 요금제 올리기.** `plan-upgrade.md`에 정리돼 있다. 더 큰 모델의 속도·정확도는 평가 세트로 비교한다

### O2 로그인 방식 비교 (2026-11-07)

조사 범위: 지금 인증 코드(`server/guard.ts`, `ui/auth-token.ts`, `App.tsx`, `migrations/0002_guard.sql`)와 Cloudflare 공식 문서(Email Service 요금·한도, Access, One-time PIN). 기호 L1~L5는 이 절에서만 쓴다(위의 R·Q·S·F·O 갈래와 다르다).

**전제: 지금 구조**

- 화면은 `createFlueClient({ token })`으로 토큰을 보내고(`App.tsx`), 가드는 `Bearer` 토큰의 해시로 D1 `users`에서 `userId`를 얻은 뒤 대화 접두어·하루 횟수·안전선을 본다
- 그래서 로그인은 "본인을 확인한 뒤 세션 토큰을 내주는 화면"으로 붙일 수 있다. `sessions`(토큰 해시, 만료)와 `identities`(로그인 수단 → `user_id`) 테이블만 더하면 Flue 클라이언트, 대화 접두어, 한도 보호는 그대로다. 로그인 수단도 나중에 하나씩 더할 수 있다
- 지금 링크로 들어온 사용자가 로그인 수단을 "등록"하면 같은 `user_id`에 연결된다. 데이터를 옮기지 않는다

**조사에서 확인한 것**

- Cloudflare 이메일 발송(Email Sending)은 아무 주소로 보내려면 Workers Paid(월 3,000통 포함)가 필요하고, 보내는 도메인이 Cloudflare DNS에 있어야 한다. 무료로는 계정에 미리 등록한 주소에만 보낼 수 있다. 지금(무료, 도메인 없음)은 매직 링크를 할 수 없다
- Cloudflare Access는 `workers.dev`에도 붙고, 이메일 일회용 코드(OTP)를 Cloudflare가 보낸다. Worker 전체 앞에 붙고, 허용할 이메일을 정책에 넣는다. Zero Trust 무료 플랜의 사용자 수 상한은 문서로 확인하지 못했다

**안마다 판단**

- L1은 로그인이 아니다. 링크를 잃는 문제가 남는다. 다만 어느 안이든 "다른 기기 추가"는 필요하니 함께 넣을 부품으로 본다
- L2는 가장 무난한 방식이지만 지금 조건(무료, 도메인 없음)에서는 막힌다. 요금제를 올리거나 도메인을 사면 다시 본다(그때 `plan-upgrade.md`에 적는다)
- L3은 비용·외부 서비스가 없고 개인정보를 더 모으지 않는다. 건강 정보(민감정보)를 다루는 서비스라 특히 좋다. 약점은 기기를 잃었을 때의 복구와 처음의 낯섦이고, 동기화되는 패스키와 지금의 링크 토큰(복구 링크)으로 메운다
- L4는 사용자를 늘릴 때 가장 강하다. 개발자 앱 등록과 개인정보 처리방침·제3자 제공 안내가 필요해 지금 단계에는 무겁다. `identities` 구조면 나중에 L3 옆에 더할 수 있다
- L5는 가장 빨리 되지만 소수 지인 시험용 문 잠금에 가깝다. 로그인 화면과 사용자 관리를 우리가 정할 수 없고, 평가 세트와 curl은 서비스 토큰을 따로 써야 한다

**추천**

1. 지금: **L3**. 패스키 로그인, 지금의 링크 토큰은 "복구·기기 추가 링크"로 둔다. L1의 기기 추가를 함께 넣는다
2. 사용자를 늘릴 때: **L4 추가**. 카카오(또는 구글)를 `identities`에 더한다. 기관 도입(O3)도 이때 본다
3. 요금제를 올리면: **L2 검토**. 이메일 복구 수단으로

Neuron은 쓰지 않는다.

**계획 단계에서 정할 것**

- 세션 토큰 보관: 지금처럼 `localStorage` + Bearer(Flue 클라이언트와 그대로 맞음) 또는 HttpOnly 쿠키(XSS에 강하지만 CSRF 대비와 클라이언트 설정 필요)
- 세션 만료 기간, "모든 기기에서 로그아웃"
- 패스키 라이브러리 선택과 Workers(WebCrypto)에서 도는지 확인. `workers.dev`는 공개 접미사라 RP ID는 `diet-coach.jjangyeesoo1.workers.dev` 전체다. 나중에 도메인을 바꾸면 패스키를 다시 등록해야 한다
- 링크 토큰 발급(`issue-token`)을 운영자 스크립트로 둘지, 로그인한 사용자가 화면에서 만들게 할지
- 기존 토큰 사용자: 지금 원격 토큰 1개의 사용자는 로그인 수단을 등록해 같은 `user_id`로 잇는다
- 가드와 계약: 대화 ID 접두어(`<userId>-…`)와 하루 30회 제한은 그대로 두고 토큰 확인을 세션 확인으로 바꾼다
